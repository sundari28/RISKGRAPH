# RISKGRAPH Synthetic Datasets

This directory contains deterministic, entirely synthetic datasets generated by the Milestone 2 data engine.

From the `backend` directory, run:

```powershell
python -m app.data_generation.generator
```

The command generates independent development and held-out test splits:

- `dev_transactions.csv` and `dev_customers.csv`: model-input records for development.
- `dev_merchants.csv`: stable merchant IDs and deterministic merchant categories.
- `dev_refunds.csv`: completed refund events linked to their original transactions.
- `dev_ground_truth.csv`: separate development labels and scenario metadata.
- `test_transactions.csv` and `test_customers.csv`: independently generated held-out model-input records.
- `test_merchants.csv` and `test_refunds.csv`: held-out merchant and refund-event records.
- `test_ground_truth.csv`: separate test labels and scenario metadata.

The default development and test seeds are different (`20260830` and `20260831`). IDs include both split and seed, and IP address ranges are isolated by split and scenario, so graph entities cannot accidentally overlap between datasets or cohorts. Transaction, customer, merchant, and refund files intentionally exclude `scenario`, `cluster_id`, and abuse labels. Ground truth contains labels for customer, transaction, and refund entities, including `COORDINATED_ABUSE_RING` cluster IDs, enabling later transaction-, customer-, and cluster-level evaluation.

Merchant topology is deliberately controlled for future graph analysis: normal, high-value, individual, and benign shared-infrastructure cohorts use disjoint merchant pools. Each abuse ring uses private merchants and at most two bridge merchants shared only with adjacent rings. This preserves limited realistic ring overlap without connecting benign or high-value activity to abuse rings through generic merchant nodes.

Each completed refund in `*_refunds.csv` has a deterministic `refund_id`, `original_transaction_id`, timestamp after the original payment, amount, and status. This permits a future graph edge from Transaction to Refund while retaining the required refund summary fields in transaction records.

No record represents a real person, payment, address, IP, or device.
